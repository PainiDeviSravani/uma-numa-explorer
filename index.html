01 / THE BASICS

First, understand the problem

Before comparing UMA and NUMA, it helps to understand why memory access becomes an important design issue when a computer has multiple processors.

01

What is a processor?

A processor executes instructions, performs calculations, and coordinates operations. A multiprocessor system contains two or more processing units that can work on different tasks at the same time.

02

Why is main memory needed?

Main memory stores the programs and data that processors need while executing tasks. When a processor requires data that is not available in its cache, it may need to access main memory.

03

Why does architecture matter?

If several processors compete for memory bandwidth or use different routes to reach data, performance can change. The memory architecture determines how processors access memory and how the system can grow.

KEY CONCEPT

Memory latency is not the same as memory bandwidth.

Latency

The time taken for a memory request to begin returning the requested data.

Bandwidth

The amount of data that can be transferred over a period of time.

Both matter. A system can have high bandwidth but still experience delays for individual memory requests.

02 / ARCHITECTURE A

UMA — Uniform Memory Access

A shared-memory architecture in which processors generally experience approximately uniform access latency to main memory under comparable conditions.

How UMA is organized

In a typical UMA system, multiple processors connect to a common main-memory system through an interconnect. The processors share a single physical memory system and can access data in the shared address space.

How a memory request works

  1. The processor requests data.

    It checks its cache and requests the data from memory if necessary.

  2. The request reaches the memory system.

    The interconnect carries the request to the appropriate memory controller or shared memory resource.

  3. Memory returns the data.

    The requested data travels back to the processor so its instructions can continue.

Important characteristics

  • Shared main-memory address space
  • Approximately uniform memory-access latency
  • Relatively straightforward programming model
  • Shared resources may become bottlenecks as demand grows

Think of it like a shared kitchen.

Advantages

  • Simple shared-memory programming model
  • Easy sharing of data between processors
  • Useful for many small and medium-sized systems

Limitations

  • Shared interconnect contention can increase
  • Memory bandwidth may limit scaling
  • Contention and cache coherence still need management

Where is it useful?

UMA-like organization is common in many conventional shared-memory multiprocessor designs, especially where a single shared memory system is practical.

03 / ARCHITECTURE B

NUMA — Non-Uniform Memory Access

A shared-address-space architecture in which memory is physically distributed among nodes. Access to local memory is generally faster than access to memory attached to another node.

Think of nearby and distant kitchens.

Each team has its own kitchen and ingredients. A team can usually get ingredients from its own kitchen more quickly. If it needs something stored in another kitchen, someone must bring it from farther away.

How NUMA is organized

A NUMA system is divided into nodes. Each node typically includes one or more processors, local memory, and an interface to the interconnect. The nodes work together as one system.

How a memory request works

  1. The processor requests data.

    The processor first checks its cache and then requests the data from the memory hierarchy.

  2. The system identifies the memory location.

    If the data is in memory local to the processor's node, the request can use the local memory path.

  3. Remote access uses the interconnect.

    If the data belongs to another node, the request may cross the node interconnect, increasing latency and consuming interconnect bandwidth.

Important characteristics

  • Memory is physically distributed across nodes
  • Processors typically share a system-wide address space
  • Local and remote memory access have different costs
  • Can scale well when memory and workloads are placed carefully

Advantages

  • More distributed memory bandwidth
  • Can support larger multiprocessor systems
  • Local memory placement can improve performance

Limitations

  • Remote memory requests can take longer
  • Data placement can affect performance
  • Operating-system and application tuning may be important

Where is it useful?

NUMA is used in many multi-socket servers and large shared-memory systems where memory capacity and bandwidth must grow with processing resources.

04 / BEYOND THE BASICS

Concepts that make the difference

UMA and NUMA are not just about where memory is located. They also affect how processors communicate, how data is shared, and how software uses the hardware.

01

Cache coherence

Each processor may have its own cache containing copies of memory data. If one processor changes a shared value, another processor must not continue using an outdated copy when the architecture requires the change to be visible.

Cache-coherence protocols help coordinate these copies. They are important in shared-memory multiprocessors, including many UMA and NUMA systems.

02

Memory consistency

Cache coherence concerns the visibility of updates to a particular memory location. Memory consistency describes the rules governing the ordering and visibility of memory operations across processors.

These rules matter when concurrent threads communicate through shared variables and synchronization mechanisms.

03

Scalability

Scalability describes how effectively a system continues to perform as processing resources increase. Adding processors does not guarantee proportional speedup.

Shared-resource contention can limit growth. NUMA can distribute memory resources across nodes, although remote accesses and interconnect traffic still matter.

04

Memory affinity and placement

In NUMA systems, the location of data can influence access time. Keeping a thread's frequently used data near the processor running that thread is often beneficial.

Operating systems can use policies such as first-touch allocation and thread affinity to influence placement. Results depend on the operating system, workload, and configuration.

Important distinction

NUMA does not mean that processors cannot access one another's memory. In a typical shared-address-space NUMA system, remote memory is accessible; it simply has a different performance cost. Also, not every NUMA system has identical cache-coherence features.

06 / SIDE-BY-SIDE COMPARISON

UMA vs NUMA

The central difference is how memory is organized and how access costs vary with memory location.

Feature UMA NUMA
Full form Uniform Memory Access Non-Uniform Memory Access
Memory organization Typically a shared main-memory system Memory distributed across nodes
Access latency Approximately uniform under comparable conditions Usually lower for local than remote memory
Address space Shared in a typical UMA multiprocessor Shared in a typical cache-coherent NUMA system
Scalability Shared resources may limit scaling Distributed memory resources can support scaling
Data placement Location is generally less visible to software Placement can significantly affect performance
Programming Often a simpler performance model May require NUMA-aware placement and tuning
Typical use Many conventional shared-memory systems Many multi-socket servers and larger systems

These are general characteristics, not absolute rules. Real systems differ in cache hierarchy, interconnect, memory controllers, and topology.

07 / PERFORMANCE IN PRACTICE

Why does memory placement matter?

Consider a server running several worker threads that repeatedly read and update data.

UMA SCENARIO

Shared memory resources

All processors access the shared memory system. If many processors generate requests at the same time, they may compete for memory bandwidth or interconnect resources.

This does not mean every UMA system is slow. Performance depends on the hardware, cache behavior, and workload.

NUMA SCENARIO

Locality-aware execution

A thread can benefit when the data it frequently uses is stored in memory local to its NUMA node. Local accesses can reduce latency and remote interconnect traffic.

If the thread repeatedly accesses remote memory, or threads frequently migrate between nodes, the expected benefit may be reduced.

A USEFUL PERFORMANCE IDEA

Execution time depends on more than processor count.

Actual performance also depends on instruction execution, cache hits and misses, memory latency, bandwidth, synchronization, and the amount of parallel work available.

Performance ≠ Number of CPUs alone

09 / APPLICATIONS

Where do these concepts matter?

Memory architecture becomes especially important when many processing threads access large amounts of shared data.

01

Database servers

Database engines may have many worker threads accessing indexes, caches, and large datasets. Memory placement can influence latency and throughput on NUMA machines.

02

Virtualization and cloud

Hosts running many virtual machines must manage processor scheduling and memory allocation. NUMA awareness can help avoid unnecessary remote-memory traffic.

03

Scientific computing

Simulations and numerical applications may process large arrays across many threads. Memory bandwidth, data partitioning, and locality can affect overall execution time.

10 / CLEAR UP THE CONFUSION

Common misconceptions

×

“NUMA is always faster than UMA.”

Not necessarily. NUMA can provide scalability and local-memory advantages, but remote accesses, workload patterns, and placement decisions can affect performance.

×

“UMA means memory access takes exactly the same time.”

Uniform means approximately uniform access latency under comparable conditions. Cache hits, contention, and other effects can still change observed latency.

×

“NUMA nodes cannot access remote memory.”

In a typical shared-address-space NUMA system, remote memory is accessible through the interconnect, but it usually has a different latency and bandwidth cost.

×

“More processors always mean proportional speedup.”

A workload may be limited by serial work, synchronization, memory bandwidth, or communication overhead. Additional processors do not remove those limits automatically.

REAL-WORLD CASE STUDY

How Swiggy Relates to UMA vs NUMA

Imagine Swiggy handling thousands of food orders at lunchtime. The system needs to process orders, update delivery status, calculate payments, and respond to users quickly.

🍔 The Real-World Problem

During peak hours, many requests arrive at the same time. If processors compete for shared memory or access data stored near another processor, memory access can become a bottleneck. This is where memory architecture becomes important.

🔵 Scenario 1: UMA Architecture

Imagine several processors handling Swiggy orders while accessing one shared main memory.

  • All processors share the same main memory.
  • Memory access time is designed to be approximately uniform.
  • Simple to manage for smaller systems.
  • Heavy shared-memory traffic can become a bottleneck.
Possible challenge: Many processors may compete for shared memory bandwidth during peak order traffic.

🟢 Scenario 2: NUMA Architecture

Imagine a large server divided into nodes. Each node has processors and its own local memory, while the nodes remain connected.

  • Each node can access its local memory faster.
  • Processors can also access memory on other nodes.
  • Remote memory access generally has higher latency.
  • Placing frequently used data near the processors that need it can help.
Possible benefit: A NUMA-aware application can improve memory locality and reduce unnecessary remote-memory access.

🍳 The Shared Kitchen Analogy

UMA: All chefs use one common kitchen storeroom. It is easy to organize, but many chefs may wait to collect ingredients from the same place.

NUMA: Each kitchen team has a nearby storeroom, while ingredients can still be collected from other teams. Nearby ingredients are quicker to access, but travelling to another storeroom takes more time.

💡 What Does This Teach Us?

For a large order-processing workload, NUMA can help when software keeps frequently accessed data close to the processors using it. However, NUMA does not automatically make every application faster. Performance depends on workload, memory placement, synchronization, and software design.

Note: Swiggy is used here as an illustrative example of a high-traffic application, not as a claim about Swiggy's actual server architecture.

11 / FINAL TAKEAWAY

One idea to remember

UMA is characterized by approximately uniform memory-access latency. NUMA distributes memory across nodes, so local and remote accesses have different costs. Understanding that difference helps explain how multiprocessor systems are designed and optimized.
